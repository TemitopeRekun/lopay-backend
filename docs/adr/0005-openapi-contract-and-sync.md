# ADR 0005 — OpenAPI is the committed API contract, synced across both repos

**Status:** Accepted
**Date:** 2026-07-11

## Context

The backend (NestJS, this repo) and the frontend (`Lopay`, React + Vite +
Capacitor) live in **two separate git repositories** with no shared package or
monorepo tooling. The API surface was described only by hand-written TypeScript
types on the frontend (`services/backend.ts`, `services/adapters.ts`), which drift
from the server silently — the audit's top documentation gap.

`@nestjs/swagger` can already emit an OpenAPI 3 document from the controllers, and
`openapi-typescript` can turn that document into a typed client. Two things were
missing: the spec was never **committed** (so nothing could diff against it), and
the generator (`scripts/generate-swagger.ts`) booted the full app — connecting to
Postgres/Firebase and requiring real secrets — so it could not run in CI or on a
fresh checkout.

The hard constraint is the two-repo split: there is no single working tree a CI
job can diff the backend spec against the frontend client in one shot.

## Decision

- **`openapi.json` is the committed source of truth for the API contract**, held
  at the **backend repo root** and regenerated by `npm run generate:swagger`.
- **The generator is hermetic.** It creates the app in Nest **preview mode**
  (`NestFactory.create(AppModule, { preview: true })`), so no provider is
  instantiated and nothing connects to Postgres, Firebase, or Redis. Env vars the
  config schema requires but the static spec does not depend on are given inert
  fallbacks, and `AppModule` is imported *dynamically after* those fallbacks are
  applied (a static import is hoisted and would validate against the un-patched
  env). Output is deterministic and byte-stable (trailing `\n`, pinned to LF via
  `.gitattributes`) so it can be diffed reliably.
- **Cross-repo sync is one command.** When the frontend repo is checked out as a
  sibling (`../Lopay`), `generate:swagger` also writes the identical `openapi.json`
  into the frontend root. The frontend commits **its own copy** so its CI is
  self-contained; the frontend's `generate:types` reads that local `./openapi.json`
  and emits the typed client `src/api.generated.ts`.
- **Each repo guards its own artifact in CI:**
  - Backend: a `generate:swagger` + `git diff --exit-code -- openapi.json` step
    fails the build if the committed spec is stale versus the code.
  - Frontend: `src/api.contract.test.ts` regenerates the client from the committed
    `openapi.json` and asserts it equals the committed `src/api.generated.ts`
    (runs under `npm test`). This catches a hand-edited client or a spec update
    that wasn't followed by `npm run generate:types`.

## Alternatives considered

- **Backend-only spec, frontend reads the sibling repo (`../lopay-backend`).**
  Rejected: the frontend's CI would have to check out a second repo to build or
  test, coupling the two pipelines. Committing a copy keeps each repo buildable
  and testable on its own.
- **Publish the client as a versioned npm package.** Heavier than warranted for
  two first-party repos; revisit if a third consumer appears.

## Consequences

- The contract is now diffable and CI-guarded on both sides; API changes surface
  as a spec diff and a client regen in the same review.
- **The FE↔BE spec copies are kept in sync by the generator, not by CI** (no CI
  job spans both repos). The workflow is: change the API → run
  `npm run generate:swagger` (updates both repos) → run `npm run generate:types`
  in the frontend → commit the spec (backend) and the spec + client (frontend). A
  backend API change that skips the frontend regen is caught at integration, not
  by a cross-repo check — an accepted limitation of the two-repo split.
- The committed spec is currently thin on descriptions: only one controller
  carries `@ApiTags`/`@ApiOperation`. Enriching the controllers so the spec is
  fully self-describing is tracked as remaining Milestone 5 documentation work;
  the contract *pipeline* landing first is what makes that enrichment safe to
  iterate on.
